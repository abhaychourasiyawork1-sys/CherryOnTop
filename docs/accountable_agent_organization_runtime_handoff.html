1. Product Thesis

The product is not primarily a workflow engine. It is a runtime for forming and operating a temporary organization of accountable software-engineering agents.

Core invariant: Every task has exactly one accountable owner. Ownership may delegate execution, but delegation never transfers ultimate accountability.
flowchart TD
    U["Client Goal"] --> R["Root Accountable Node"]
    R --> P["Plan the outcome"]
    P --> D{"Can I solve this myself?"}
    D -- "Yes" --> E["Execute"]
    D -- "No / inefficient" --> G["Delegation Economics"]
    G --> C{"Delegation justified?"}
    C -- "No" --> E
    C -- "Yes" --> N["Create Child Commitment"]
    N --> CH["Child Accountable Node"]
    CH --> H["Handoff: status + evidence + artifacts"]
    H --> R
    E --> V["Verify"]
    V --> F{"Definition of Done met?"}
    F -- "No" --> RP["Re-plan / recover / delegate"]
    RP --> P
    F -- "Yes" --> OUT["Deliver outcome"]

What problem this solves

Accountability gapAgents often produce outputs without owning the outcome. The node contract makes ownership explicit and observable.
Static orchestrationFixed graphs decide the organization before the work is understood. Here, nodes can recursively form the team they need.
Runtime lock-inThe organization is not tied to one vendor or harness. Nodes choose from available runtimes through adapters.
Context overloadParents do not need every child token. Structured handoffs compress operational knowledge while artifacts remain inspectable.
Unbounded swarmsDelegation is an economic decision constrained by budget, latency, coordination cost, authority, and risk.
Repeated rediscoveryValidated local experience can become organizational memory and improve future routing and planning.

Control plane vs. agency

Organization RuntimeEnforces lifecycle, policy, budgets, authority, state, scheduling, events, and isolation. It should not secretly become the manager of every decision.
Accountable NodesOwn goals, commitments, plans, delegation choices, runtime choices, verification, and completion.
Intelligence PlaneProvides evidence and candidates. It advises; it does not own the task.
Execution PlaneProvides interchangeable harnesses and tools. It executes the node's chosen approach.
The architectural mental model is: Organization Runtime = infrastructure + guardrails; Nodes = agency + responsibility.

Server / Host: one process for v0.1, two interfaces forever

The Organization Runtime is not a monolith. It is built as two logical components — modeled on the comparable split used by Omnigent — colocated in a single OS process for v0.1, but never sharing state through anything other than their defined interface:

ServerOwns all durable state and the node lifecycle logic. Exposes the only API the CLI (and any future GUI) talk to.
HostOwns Kubernetes dispatch, the runtime adapter registry, and Secret lifecycle. Never touches SQLite directly.
Why split at all if they're colocated? Because "remote workers" is already on this document's own roadmap (§22, v0.4). If Server and Host share one undifferentiated codebase now, giving Host its own machine later is a rewrite. If they only ever talk through one defined interface, it's a deployment change. See §17 for the full daemon-lifecycle and API design.

A node is the fundamental accountable unit. It is a persistent goal-oriented worker that can plan, execute, delegate, verify, and re-plan.

Node contract

{
  "goal": "Implement OAuth login",
  "definition_of_done": [
    "OAuth provider integrated",
    "tests pass",
    "security review complete",
    "PR ready"

  "deadline": {
    "expected_at": "...",
    "hard_at": "..."
  }
}

Node responsibilities

  • Understand its goal and current state.
  • Maintain a plan that can change as evidence changes.
  • Choose whether to self-execute or delegate.
  • Request intelligence when uncertainty justifies it.
  • Choose a runtime from candidates.
  • Operate within authority and economic envelopes.
  • Maintain commitments and report temporal risk.
  • Verify outcomes against the Definition of Done.
  • Produce structured handoffs and durable artifacts.
  • Escalate when it cannot safely or economically complete the outcome.

5. Node Lifecycle

The lifecycle borrows the useful idea of a persistent iterative loop from Fractal, but expands it with intelligence, commitment management, economics, and explicit accountability.

stateDiagram-v2
    [*] --> CREATED
    CREATED --> ORIENT
    ORIENT --> PLAN
    PLAN --> INTELLIGENCE_GATE
    INTELLIGENCE_GATE --> PLAN: evidence needed
    INTELLIGENCE_GATE --> EXECUTION_DECISION: enough context
    EXECUTION_DECISION --> SELF_EXECUTE
    EXECUTION_DECISION --> DELEGATE
    DELEGATE --> WAIT_CHILD
    WAIT_CHILD --> REPLAN
    SELF_EXECUTE --> VERIFY
    WAIT_CHILD --> REPLAN: handoff
    VERIFY --> COMPLETE: DoD satisfied
    VERIFY --> REPLAN: gap / failure
    REPLAN --> INTELLIGENCE_GATE
    REPLAN --> ESCALATE: authority / budget / deadline boundary
    ESCALATE --> WAIT_APPROVAL
    WAIT_APPROVAL --> PLAN
    COMPLETE --> [*]

Iteration anatomy

1 · Observe
Read goal, commitments, messages, child state, artifacts, repository state, deadlines, budget, and relevant memory.
2 · Orient
Determine what is known, unknown, blocked, stale, and at risk.
3 · Plan
Define the next smallest useful execution strategy and decide whether decomposition is warranted.
4 · Intelligence Gate
Estimate uncertainty. Reuse memory first; spawn targeted intelligence only when needed.
5 · Execution Decision
Self-execute or delegate using delegation economics.
6 · Runtime Selection
Ask the runtime registry/intelligence layer for candidates; node chooses.
7 · Execute
Run work through a runtime adapter inside the allowed environment.
8 · Verify
Compare actual result with Definition of Done and evidence requirements.
9 · Commit / Handoff
Persist artifacts, decision records, state, and a concise handoff.
10 · Re-plan / Complete
Continue, delegate, recover, escalate, or complete.

Fractal currently implements a run → iteration → step hierarchy, discovers step files each iteration, records execution in local SQLite, and supports bounded time/cost/depth/child controls. This proposal treats those as inspiration and adds product-specific primitives around them. Fractal iteration-loop reference.

Implementation note (§17): this diagram is deliberately drawn as a statechart because it is one — implemented directly with XState rather than a hand-rolled switch/if state machine, so the states and transitions above map 1:1 onto code.

Nodes should be runtime-agnostic. The organization should be able to use the user's existing subscriptions and local harnesses instead of forcing a new model billing layer.

    NODE --> CHOOSE["Node chooses runtime"]
    CHOOSE --> ADAPT["Runtime Adapter"]
    ADAPT --> CLAUDE["Claude Code"]

Adapter contract

RuntimeAdapter
  discover() -> RuntimeDescriptor
  validate(request, authority) -> Validation
  estimate(request) -> CostLatencyEstimate

  stream(handle) -> Events
  stop(handle) -> StopResult
  collect_usage(handle) -> Usage
  normalize_result(handle) -> ExecutionResult

Runtime descriptor

{
  "runtime": "codex",
  "installed": true,
  "authenticated": true,
  "subscription_available": true,
  "capabilities": ["repo", "shell", "coding"],
  "models": ["..."],
  "supports": {
    "streaming": true,
    "budget_limit": false,
    "parallel_sessions": true
  }
}
Decision boundary: The runtime registry says what is available and the intelligence layer says what looks promising. The accountable node makes the final selection.

How launch() actually drives a harness

Adapters invoke each CLI in its built-in headless / non-interactive streaming mode — e.g. Claude Code's --print --output-format stream-json — and parse the result as structured events (tool calls, messages, results), the same mode the Claude Agent SDK itself is built on. No PTY, no ANSI-escape scraping of rendered terminal output. If a future harness genuinely has no scriptable mode, the adapter falls back to capturing plain stdout/stderr and the exit code rather than driving a pseudo-terminal.

Concretely (§17): the subprocess itself is spawned with execa, and its stdout is piped through ndjson's parse transform to get one structured event object per line — no hand-rolled buffering or JSON.parse-per-chunk logic.

Fractal currently supports several coding-agent backends and per-node/per-step agent, provider, model, and effort overrides. See Fractal Agent Backends.

Authority is distinct from capability. A runtime may technically be able to do something while a particular node is not permitted to do it.

CapabilityWhat the runtime/tool can technically do.
AuthorityWhat the node is permitted to do.

effective_authority(child)
  = platform_maximum
    ∩ parent_granted_subset
    ∩ child_requested_scope
    ∩ runtime_capabilities

Security lesson from Fractal, resolved: Git worktrees isolate branches, not the rest of the machine — the Fractal README itself warns that unattended agents can have broad shell/network/credential access. Rather than accepting that as a documented risk, v0.1 closes it structurally: every execution step runs inside a disposable, network-restricted Kubernetes Job, not directly on the host. Authority still governs what a node is permitted to request; the Job's Secret/network scope is the hard backstop underneath it regardless. Full mechanism in §18.

Reserve is intentional. A capable node should not spend its entire budget on the initial plan. It should retain resources for failure recovery, runtime switching, and unexpected dependencies.

The v0.1 scoring formula

Delegation is decided by a transparent weighted heuristic, deliberately not by asking the harness's own reasoning to judge — every number behind the decision must be printable and reproducible, or "delegation is economic" is just a slogan rather than an evidence-backed decision:

score = estimated_value_of_delegating
        − (model_cost + latency_cost + coordination_cost + verification_cost)
        − risk_penalty

delegate if score >= configurable_threshold, else self-execute

Inputs are cheap, already-available signals: task-class complexity from the Intelligence Bundle, remaining budget/deadline slack from the node's own commitment, and historical actuals for similar past tasks from node/org memory — falling back to conservative defaults when no history exists yet. The formula improves purely by accumulating history; no model training is required for v0.1.

11. Memory & Organizational Learning

Memory is hierarchical: working context is local, durable experience is node-local, and validated patterns can propagate upward into organizational memory.

flowchart TB
    W["Working Memory"] --> N["Node Memory"]
    N --> C["Candidate Learning"]
    C --> V{"Evidence / repeated validation?"}
    V -- "No" --> N
    V -- "Yes" --> O["Organizational Memory"]
    O --> FUT["Future Intelligence / Routing"]

Three levels

Working MemoryCurrent task context, observations, plan, immediate reasoning. Short-lived and runtime-oriented.
Node MemoryPersistent local experience: findings, failures, decisions, artifacts, prior commitments, useful procedures.
Organizational MemoryValidated reusable knowledge: runtime performance, strategies, failure modes, capability mappings, historical estimates.

Promotion rule

Local experience
      ↓
Candidate learning
      ↓
Evidence / provenance
      ↓
Validation or repeated outcomes
      ↓
Promote to organizational memory
Do not treat every agent statement as organizational truth. Organizational memory should be a curated evidence-backed layer, not a transcript dump.

14. Failure & Recovery

Failure is normal. The system should preserve state, classify failure, and choose the cheapest safe recovery path rather than blindly retrying.

flowchart TB
    X["Execution"] --> F{"Failure / anomaly"}
    F --> C{"Classify"}
    C --> T["Transient"]
    C --> K["Capability gap"]
    C --> A["Authority boundary"]
    C --> B["Budget / time risk"]
    C --> D["Bad plan"]
    C --> S["Security / policy"]
    T --> RT["Retry / alternate runtime"]
    K --> RC["Request capability / delegate"]
    A --> ESC["Escalate for approval"]
    B --> ECON["Re-plan economically"]
    D --> RP["Re-plan"]
    S --> STOP["Stop + preserve state"]
    RT --> V["Verify"]
    RC --> V
    ESC --> V
    ECON --> V
    RP --> V

Recovery hierarchy

  1. Retry only when failure is plausibly transient.
  2. Change runtime when the selected runtime is the problem.
  3. Change plan when the approach is wrong.
  4. Delegate when a capability or context gap is the bottleneck.
  5. Escalate when authority, budget, deadline, or external consent is required.
  6. Stop safely when policy/security boundaries are reached.

Failure evidence

Every failed attempt should retain enough structured evidence to answer: what was attempted, by whom, with what runtime, under what authority, what failed, what changed, what it cost, and what the next recovery action is.

Do not allow failure handling to become recursive chaos. Recovery itself should be subject to delegation economics and authority limits.

17. Implementation Architecture & Tech Stack

Everything above this section is conceptual and stack-agnostic. This section is where each concept becomes a specific, buildable choice — the outcome of a dedicated implementation-level brainstorming pass.

Daemon lifecycle

The daemon (Server+Host, §3) persists across CLI invocations — required for org watch and desktop-notification approvals to mean anything. org run detects whether one is already running (a local Unix domain socket / lock file) and auto-spawns it if not, including first-run kind cluster bootstrap. Every other command is a thin client hitting the Server's HTTP+WebSocket API. org daemon start / status / stop gives explicit control when needed.

Persistence: CRUD tables + append-only event log

SQLite via better-sqlite3, deliberately not full event sourcing. Mutable state tables (nodes, commitments, decisions, budgets) answer "what's true right now" without replaying history — the query patterns the CLI actually needs (org tree, commitment risk, decision inspection) are simplest against direct state. A separate append-only events table records every transition, giving org events, crash-recovery, and the audit trail the accountability model depends on — without the snapshot/projection machinery full event sourcing would require before there's evidence it's needed.

18. Execution Substrate & Security

The original architecture flagged git-worktree isolation as a real, named risk rather than assuming it was sufficient. This section is how that risk gets closed structurally, not just documented.

Deliberate trade-off: Kubernetes-per-execution sandboxing was chosen over a lighter policy-only MVP option, even for a single local user. It means Docker + a local kind cluster become real v0.1 prerequisites, not an optional hardening pass — a heavier first-run bar in exchange for closing the risk immediately instead of deferring it.

Cluster bootstrap

On first use, if no kubeconfig/cluster is detected, the CLI provisions a local kind (Kubernetes-in-Docker) cluster automatically — one dependency (Docker) instead of two, and the cluster is disposable/recreatable. If a kubeconfig already points somewhere — a real cluster, Docker Desktop's K8s, a shared org cluster — that's used instead. The same code path scales from laptop to production cluster without changes.

Execution granularity: one Job per step, not per node

Every time a node's lifecycle reaches Execute and calls a runtime adapter, that's a single Kubernetes Job with the worktree mounted in — runs to completion, streams results back, then the pod terminates. The node itself stays an in-memory state machine in the daemon (§3/§4) that can spawn many such Jobs across its iteration loop. This keeps pods short-lived and disposable and avoids re-introducing per-node OS-process complexity.

Container image strategy

One shared base runner image (org/runner) with all supported harness CLIs, git, and common toolchains pre-installed — built from a Dockerfile in-repo, published to GHCR on release, pulled at a pinned tag by default with local-build fallback. Simplest to reason about; per-adapter or user-pluggable images are deferred until a concrete need for image customization shows up.

Credential injection

flowchart LR
    LOCAL["User's local auth
(Claude Code/Codex login, git creds)"] --> DAEMON["Daemon reads once"]
    DAEMON --> SEC["Create Job-scoped K8s Secret"]
    SEC --> POD["Mounted read-only in pod"]
    POD --> DONE["Job completes"]
    DONE --> DEL["Secret deleted"]

Per-Job Kubernetes Secrets, mounted read-only, created immediately before the Job and deleted on completion. The daemon relays the user's existing local credentials rather than asking for new ones — subscription-based auth keeps working, and nothing long-lived sits in the cluster.

Network policy

DirectionDefault
IngressDenied entirely — nothing initiates a connection into a Job pod.
EgressDenied by default; allowlisted per Job to the LLM provider endpoint, the task's git remote, and package registries only if the Definition of Done requires installing dependencies.
Pod-to-pod / cluster-internalBlocked — nodes coordinate through the daemon, never directly with each other's pods.
Ties back to §8's authority model: capability (what a pod can technically reach) is now hard-bounded by NetworkPolicy and Secret scope, independent of whatever authority a node was granted — the "capability ∩ authority ∩ sandbox" formula in §8 has a real, enforced third term for the first time, not just a documented intention.

19. Product Framing & Identity

Prompted by how effectively Munder Difflin uses narrative metaphor — an "office of agents," a named orchestrator, "desks" — to make an abstract multi-agent system feel concrete and demo-able.

The decision here is deliberately restrained: adopt a light organizational metaphor, not a new mascot or persona. The vocabulary this document already uses — organization, accountable owner, delegation, commitment, authority, handoff — is the product's voice. CLI output, docs, and any future landing page or GUI should talk about "the organization" and "handoffs," not generic "agents" and "tasks." What this changes in practiceorg tree output, error messages, and escalation notifications use "accountable owner," "commitment," "handoff" — not "worker," "job," "task." Section/command naming throughout this document already does this; keep it consistent going forward.
What this explicitly defersA distinct visual brand identity, a named mascot/character, or marketing-site-level creative work — real investment, kept separate from and not blocking the architecture and implementation work.
The presentation lesson worth keeping from Munder Difflin beyond naming: lead with what you can do (a live org watch view, a real PR delivered) before how it's built — progressive disclosure, not architecture-first, when this product is eventually shown to someone outside this document.

23. Decisions Log — Brainstorming Session

This section records the decisions that converged during the conversation so the handoff preserves not only the architecture but the reasoning behind it.

D1 Hierarchical ownership — Adopted model C: every task has an accountable owner, with recursive children.
D2 Hybrid runtime selection — Intelligence/router provides candidates; the accountable node chooses the runtime.
D3 Dual communication — Structured messages for coordination plus durable artifacts for knowledge.
D4 Goal-contract delegation — Parent gives goal, constraints, Definition of Done, and authority; child owns plan and execution.
D5 Temporal commitments — Commitments include expected time, hard deadline, progress timestamps, risks, evidence, and next checks.
D6 Hybrid authority — Platform defines maximum authority; parents grant subsets; children operate autonomously inside them.
D7 Delegation economics — Delegation is an explicit value-vs-total-cost-vs-risk decision.
D8 Intelligence coordinator — One coordinator lazily invokes specialized intelligence workers when uncertainty justifies it.
D9 Hierarchical memory — Local memory first; validated learnings can be promoted into organizational memory.
D10 SDE-first — First domain is software engineering; abstractions remain domain-extensible.
D11 Local-first CLI — Execution initially happens on the user's machine using existing subscriptions/harnesses. GUI comes later.
D12 Fractal as inspiration — Borrow recursive nodes, iteration, worktrees, messaging, plans, bounds, and local state; do not simply fork the architecture.

Session 2 (implementation-level pass) added the following, resolving the parts of the architecture above that were left conceptual:

D13 Pure TypeScript stack — No polyglot split for v0.1. Intelligence-plane workers are constrained runtime-adapter invocations, not a separate Python/ML stack. One dependency graph, one build/debug story.
D14 Nodes are in-memory, not OS processes — A single daemon holds the whole node tree as in-memory state machines checkpointed to SQLite. Only a node's execution step ever leaves the daemon.
D15 Headless/structured adapter execution — Adapters drive each harness in its built-in non-interactive streaming mode (as the Claude Agent SDK itself does), not PTY-scraped terminal output.
D16 CRUD state + append-only event log — Not full event sourcing. State tables answer "what's true now"; the events table is the audit/replay trail.
D17 Plain-text CLI + one live TUI — Scriptable text output by default; org watch is the one Ink-based live dashboard.
D18 Kubernetes sandboxing from v0.1 — Chosen deliberately over a lighter policy-only MVP option, because the architecture's own worktree-isolation risk (see §18) needed a real, not documented-only, mitigation — even for a single local user.
D19 Auto-provisioned local kind cluster — Zero manual cluster setup; an existing kubeconfig is used instead if one is already configured, so the same code path scales from laptop to production cluster.
D20 Job-per-execution-step granularity — One Kubernetes Job per harness invocation, not one pod per node's lifetime. Keeps pods short-lived and disposable.
D21 Ephemeral per-Job credentials — K8s Secrets scoped to a single Job, mounted read-only, deleted on completion. Nothing long-lived sits in the cluster.
D22 npm packaging with preflight checks — org doctor verifies Docker/kind/kubectl before first run rather than failing opaquely mid-task.
D23 Structured logs over tracing infra — pino logs plus the events table are sufficient for v0.1; OpenTelemetry is deferred until concurrent-Job correlation is a proven need.
D24 Light organizational metaphor, no mascot — The existing vocabulary (organization, owner, delegation, commitment, handoff) is the product's voice, inspired by how Munder Difflin's narrative framing makes a multi-agent system feel concrete — without a separate creative/brand exercise.
D25 Default-deny network with a per-Job allowlist — Egress limited to the LLM provider, the task's git remote, and package registries only when the DoD needs installs.
D26 Approval escalation via TUI + OS notification — Not a blocking terminal prompt, since node execution is backgrounded and concurrent by design.
D27 Logical Server/Host split, colocated for v0.1 — Modeled on Omnigent's comparable production architecture (a meta-harness orchestrating Claude Code/Codex/Cursor/Pi with its own Server/Host-daemon split), so a future remote-worker version is a deployment change, not a redesign.
D28 Transparent weighted-heuristic economics — Not LLM judgment. Every delegation decision must be printable and reproducible to stay evidence-backed, per the architecture's own accountability principle.
D29 One shared base runner image — All supported harnesses pre-installed in a single published image for v0.1, not per-adapter or user-pluggable images.

Session 3 (library-research pass, 2026-09-05) replaced hand-rolled pieces of the stack with researched, actively-maintained, widely-adopted libraries — verified via live search, not assumed:

D30 zod for all validation — 100M+ weekly downloads, the de facto TS validation standard; node contracts, CLI args, and tRPC inputs all validated in one place.
D31 tRPC over hand-written REST — Official Fastify + WebSocket adapters give end-to-end typesafe daemon↔CLI procedures with zero codegen, replacing hand-written routes and duplicated types.
D32 Drizzle ORM over raw SQL — ~2M weekly downloads; schema-in-TypeScript and generated migrations layered on the existing better-sqlite3 driver, replacing hand-written SQL strings and migration scripts.
D33 XState for the node lifecycle — Implements §5's CREATED→...→COMPLETE statechart directly instead of a hand-rolled FSM; zero-dependency, widely used for backend workflow orchestration.
D34 execa for all process execution — ~128M weekly downloads; standard replacement for raw child_process across adapters and Host-side shelling to kind/kubectl/git.
D35 ndjson for harness output — Standard streaming NDJSON parser for Claude Code's stream-json events, replacing a hand-rolled line-buffering parser.
D36 pm2 for daemon lifecycle — ~2.8-3.6M weekly downloads, 600M+ total; production-grade start/stop/status and crash auto-restart via its programmatic API, replacing hand-rolled detached-process/PID-file logic.
D37 @clack/prompts + listr2 + @inkjs/ui for CLI/TUI polish — Modern, purpose-built, actively maintained libraries for org doctor prompts/task lists and org watch widgets, instead of hand-rolled equivalents.
D38 @kubernetes/client-node and node-notifier reconfirmed — Both independently verified as still the correct, actively-maintained choice; no change from D15/earlier picks.
D39 No JS wrapper for kind, and no command-exists dependency — Researched and confirmed no viable npm-native kind binding exists (shelling out via execa stands); deliberately skipped adding a dependency for binary-existence checks since the common package is 6+ years unmaintained and execa's own error path covers it in one line.

One-sentence product definition

A recursively organized network of accountable software-engineering agent nodes that autonomously plan, delegate, select capabilities and runtimes, manage commitments, and optimize execution under explicit authority and economic constraints.

Core invariant

Every task has one accountable owner; ownership can delegate execution but never accountability.
